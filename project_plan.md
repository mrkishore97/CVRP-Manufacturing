# Manufacturing PO Route Optimizer — Project Plan

**Document version:** 1.0  
**Created:** 2026-06-21  
**Status:** Approved for implementation  
**Reference project:** `../CVRP_PDP_Streamlit-master/`

## 1. Purpose

Build a production-oriented planning application for a manufacturing plant that assigns purchase-order pickup, drop, and pickup–drop movements to available trucks while respecting:

- PO readiness times and hard due dates.
- Vehicle capacities and working shifts.
- Pickup-before-delivery precedence.
- Same-vehicle requirements for paired movements.
- Road travel distance and duration obtained from Google Maps.
- Plant departure and return rules.

The application will use a standalone backend and a replaceable Streamlit frontend. The backend must remain usable by a future web, mobile, Power Apps, or other frontend without importing Streamlit.

The system must not return only a generic “no solution” result. When the full workload cannot be completed before its deadlines, it must identify the affected POs, provide the most useful reason available, and preserve a feasible partial plan when possible.

## 2. Delivery principles

No software can be guaranteed to be literally error-proof. This project will instead use defensive validation, strict interfaces, deterministic tests, controlled external API behavior, and milestone quality gates designed to catch defects at the stage where they are introduced.

The following rules apply throughout implementation:

1. No milestone starts until the previous milestone gate passes.
2. Backend code never imports Streamlit or reads Streamlit session state.
3. Domain and solver tests never require a live Google API key.
4. A routing API failure is reported explicitly; the application never silently substitutes straight-line distance in a production plan.
5. All datetimes are timezone-aware. The plant timezone is used for input and display, and UTC is used internally.
6. User-facing quantities are positive. Internal pickup and delivery load changes are generated by the backend.
7. Google calls occur only after an explicit user action and are cached; Streamlit reruns must not cause repeated billable calls.
8. Every solver result is independently validated before it is returned to the frontend.
9. Invalid input fails early with row-level messages.
10. Existing reference files remain untouched.

## 3. Confirmed working assumptions

These defaults were accepted with the initial plan and will be made configurable where practical:

- All trucks start at the manufacturing plant.
- Trucks return to the plant at the end of each shift.
- Planning may span multiple days.
- A physical truck can have one logical shift per operating day.
- A pickup task means supplier to plant.
- A drop task means plant to customer or destination.
- A pickup–drop task means supplier/origin to a separate destination.
- For an inbound pickup, the default deadline applies to arrival and unloading at the plant.
- For a drop or pickup–drop pair, the default deadline applies to completion at the final drop.
- The task editor will allow the deadline event to be changed when operational rules differ.
- A date-only deadline is normalized to the end of the applicable truck shift and is displayed as an explicit datetime before solving.
- Travel mode is driving.
- Google route durations are a planning estimate, not a guarantee against real-world delays.

Any change to these assumptions must first update the domain contract, affected tests, and this document.

## 4. Scope

### 4.1 Version 1 scope

- One manufacturing plant/depot.
- Any number of trucks, with three trucks as the primary acceptance scenario.
- Mixed pickup, drop, and pickup–drop tasks in one plan.
- Manual task entry and CSV/XLSX import.
- Manual fleet entry.
- Multi-day planning horizon using truck shifts.
- Google address geocoding.
- Google road distance and duration matrices.
- Capacity, readiness, deadline, shift, precedence, and route-duration constraints.
- Hard-deadline solve and relaxed diagnostic solve.
- Route tables, timeline details, map, and CSV/XLSX export.
- Saved planning scenarios and matrix cache using SQLite.
- FastAPI backend with versioned JSON endpoints.
- Streamlit frontend using only the backend API.
- Automated unit, integration, API, solver, and frontend smoke tests.
- Local Windows startup instructions and script.

### 4.2 Explicitly out of scope for Version 1

- Multiple plants or cross-docking between depots.
- Live driver mobile tracking.
- Dispatch changes while trucks are already on the road.
- Driver payroll, hours-of-service regulatory calculations, or electronic logs.
- Automatic ERP write-back.
- Continuous time-dependent travel durations throughout a route.
- Exact traffic prediction for future dates.
- Advanced loading constraints such as pallet position, axle weight, temperature zones, or three-dimensional packing.
- User authentication and enterprise role management.

The architecture must allow these capabilities to be added later without moving optimization logic into the frontend.

## 5. Reference application assessment

The existing application provides useful examples for:

- OR-Tools `RoutingModel` setup.
- Capacity constraints.
- Pickup and delivery precedence.
- Basic Streamlit input patterns.
- Folium route display.
- Route result presentation.

The new application will not copy the following design limitations:

- A single file containing UI, geocoding, solver, and map logic.
- Nominatim geocoding and geodesic/straight-line distance as the routing cost.
- Negative demand entered directly by users.
- Hidden depot duplication in the UI data model.
- Generic “No solution found” feedback.
- No travel-time, shift, readiness, or deadline constraints.
- Streamlit session state acting as the application database.

## 7. Core domain model

### 7.1 Location

- `location_id`: stable internal identifier.
- `name`: user-friendly name.
- `address`: entered address.
- `formatted_address`: provider-normalized address.
- `place_id`: Google place identifier when available.
- `latitude`, `longitude`.
- `geocode_status` and optional warning.

Duplicate physical locations are deduplicated for matrix calculation but retain task-level identities.

### 7.2 Task

- `task_id`: unique ID.
- `po_number`: business identifier.
- `task_type`: `PICKUP`, `DROP`, or `PICKUP_DROP`.
- `origin_location_id`.
- `destination_location_id`.
- `quantity`: positive decimal or integer according to configured unit.
- `ready_at`: earliest service start.
- `due_at`: hard completion deadline.
- `due_event`: `PICKUP_COMPLETE` or `DELIVERY_COMPLETE`.
- `pickup_service_minutes`.
- `delivery_service_minutes`.
- `priority`.
- `required_vehicle_tags`: optional compatibility tags.
- `notes`.

Every task is expanded internally into a pickup node and delivery node:

- Pickup: supplier pickup node -> plant delivery node.
- Drop: plant pickup node -> customer delivery node.
- Pickup–drop: origin pickup node -> destination delivery node.

This unified representation makes load and precedence behavior consistent for all task types.

### 7.3 Vehicle and vehicle shift

**Vehicle**

- `vehicle_id`, name, capacity, tags, enabled status.
- Optional maximum route distance and duration.

**VehicleShift**

- `shift_id` and physical `vehicle_id`.
- Start/end depot.
- `shift_start` and `shift_end`.
- Optional cost and availability override.

The solver receives vehicle shifts, not raw physical vehicles. This supports multi-day planning without pretending a truck can work several days in one continuous route.

### 7.4 Routing matrix

- Ordered location IDs.
- Asymmetric `distance_meters` matrix.
- Asymmetric `duration_seconds` matrix.
- Unreachable element statuses.
- Provider, travel mode, routing preference, and departure-time bucket.
- Creation and expiry timestamps.

### 7.5 Plan result

- Overall status: `FEASIBLE`, `PARTIALLY_FEASIBLE`, `INFEASIBLE`, or `INVALID_INPUT`.
- Route for each used vehicle shift.
- Ordered route stops with arrival, service start, departure, load, distance, deadline, and slack.
- Total distance, driving time, service time, waiting time, and truck-shifts used.
- Scheduled task IDs.
- Unscheduled or late task diagnostics.
- Solver metadata and warnings.
- Matrix metadata used for the plan.

## 8. Datetime and deadline rules

Datetime mistakes can invalidate a route plan, so the following rules are mandatory:

1. The planning request includes an IANA timezone, defaulting to `America/Toronto`.
2. Imported naive datetimes are interpreted in the selected plant timezone.
3. Ambiguous or nonexistent daylight-saving times are rejected with a row-level error.
4. Datetimes are converted to integer seconds from a planning-horizon origin for OR-Tools.
5. Date-only deadlines are converted to the relevant shift end, not silently to midnight.
6. The normalized deadline is shown in the validation preview.
7. A completion deadline is enforced against departure from the due node, not merely arrival. Internally, the latest allowed arrival is `due_at - service_duration`.
8. A task with `ready_at > due_at` is rejected before matrix calculation.
9. A task outside the planning horizon is reported explicitly.

## 9. Google routing design

### 9.1 Provider abstraction

Define a `RoutingProvider` interface with methods for:

- `geocode(addresses)`.
- `compute_matrix(locations, routing_options)`.
- Optional `compute_route_polyline(ordered_stops)`.

Implementations:

- `GoogleRoutingProvider` for production.
- `FakeRoutingProvider` for tests, demos, and offline development.

### 9.2 Google services

- Use the Google Geocoding API for address resolution.
- Use the Google Routes API `Compute Route Matrix` endpoint for road distance and duration.
- Do not build new production behavior on the legacy Distance Matrix API.
- Use driving mode and a configurable routing preference.
- Store the API key only in backend environment configuration.

### 9.3 Call safety

- Deduplicate locations before computing a matrix.
- Calculate and display matrix element count before the call.
- Split requests according to provider limits.
- Use connection/read timeouts, bounded retries, and exponential backoff with jitter.
- Retry only transient failures such as throttling or server errors.
- Never retry invalid requests indefinitely.
- Validate that every returned origin/destination index maps to the request.
- Mark unreachable pairs explicitly.
- Reject partial or malformed provider responses.
- Redact API keys and sensitive headers from logs.

### 9.4 Cache behavior

Use SQLite for a persistent cache keyed by:

- Provider.
- Origin and destination place IDs or stable coordinate hashes.
- Travel mode and routing preference.
- Departure-time bucket when applicable.
- Relevant provider options.

Cache entries include schema version and expiry. A schema or routing-option change must not reuse incompatible entries.

## 10. Optimization design

### 10.1 OR-Tools dimensions and constraints

**Capacity dimension**

- Pickup node adds quantity.
- Delivery node subtracts quantity.
- Load must remain from zero through vehicle capacity.
- A task quantity above all compatible vehicle capacities fails prevalidation.

**Time dimension**

- Transit equals service time at the current node plus travel duration to the next node.
- Waiting slack is allowed when a truck arrives before a task is ready.
- Start/end cumul bounds equal the vehicle shift.
- Ready time is a lower bound at the applicable node.
- Due time is a hard upper bound at the selected completion event.

**Pair constraints**

- Pickup and delivery use the same vehicle shift.
- Pickup occurs before delivery.
- Paired nodes are activated or dropped together in diagnostic mode.

**Route constraints**

- Start and end at configured depot nodes.
- Respect optional route distance and duration limits.
- Respect vehicle compatibility tags.

### 10.2 Objective

Strict solve priorities:

1. Serve every valid task within hard constraints.
2. Minimize truck-shifts used using vehicle fixed costs.
3. Minimize travel duration/distance.
4. Reduce maximum route span to avoid severe imbalance.

Weights will be centralized in configuration and covered by regression tests. Objective weights must not be scattered through UI code.

### 10.3 Solver controls

- Deterministic random seed where supported.
- Configurable search time limit.
- Explicit first-solution and local-search strategies.
- Return timeout status separately from proven infeasibility.
- Record solver duration and configuration in result metadata.
- Never treat a timeout with no solution as proof that no feasible plan exists.

### 10.4 Independent result validation

Before returning a route plan, a separate validator must recalculate and verify:

- Each scheduled task appears exactly once.
- Each pair uses one vehicle and correct order.
- No truck exceeds capacity at any stop.
- Every service begins after readiness.
- Every hard deadline is met.
- Every route remains inside its shift.
- Start/end depot rules are met.
- Reported totals equal the sum of route legs.

If validation fails, return an internal plan-validation error and retain diagnostic details in server logs; do not display an invalid route as successful.

## 11. Infeasibility diagnostics

Diagnostics run in layers so simple causes are reported without relying entirely on a solver explanation.

### 11.1 Static prechecks

- Missing or duplicate task IDs.
- Empty or unresolved address.
- Nonpositive quantity.
- Quantity over all compatible truck capacities.
- Invalid task-type address combination.
- `ready_at > due_at`.
- No compatible or available vehicle shift.
- Deadline outside the planning horizon.
- Required matrix leg unreachable.

### 11.2 Earliest-completion checks

For each task independently, calculate a lower-bound completion time using:

- Earliest compatible shift start.
- Travel to origin.
- Pickup service.
- Travel to destination.
- Delivery service.

If this lower bound is after the deadline, report the task as individually deadline-infeasible.

### 11.3 Strict solve

Attempt a plan in which all valid tasks are mandatory and deadlines are hard.

### 11.4 Relaxed diagnostic solve

If the strict solve returns no solution:

- Keep capacity, precedence, pairing, and shift safety hard.
- Allow task dropping with a very high priority-sensitive penalty.
- Apply lateness penalties in a separate diagnostic model where safe.
- Couple activation of pickup and delivery nodes.
- Return the best feasible subset and identify late/dropped tasks.

### 11.5 User-facing diagnostic categories

- `INVALID_ADDRESS`
- `INVALID_TASK`
- `CAPACITY_EXCEEDED`
- `NO_COMPATIBLE_TRUCK`
- `OUTSIDE_PLANNING_HORIZON`
- `UNREACHABLE_ROUTE`
- `DEADLINE_IMPOSSIBLE_INDIVIDUALLY`
- `INSUFFICIENT_COMBINED_FLEET_TIME`
- `SOLVER_TIMEOUT`
- `UNKNOWN_INFEASIBILITY`

Messages include PO number, due datetime, best estimated completion when available, lateness, and a suggested corrective action.

### 14.1 Persistence

SQLite stores:

- Matrix cache.
- Saved scenarios.
- Plan results and metadata.
- Schema version.

Repository interfaces isolate SQLite from application services so another database can replace it later.

### 14.2 Configuration

Backend environment settings include:

- Google API key.
- Database path.
- Default timezone.
- API timeout and retry settings.
- Matrix cache expiry.
- Solver time limits.
- Maximum tasks/locations.
- Logging level.

An `.env.example` contains names and safe examples, never credentials.

### 14.3 Security controls

- API key excluded from source control.
- `.env`, Streamlit secrets, databases, logs, and exports excluded where appropriate.
- Secret values redacted from exceptions and logs.
- Inputs validated for size and type.
- Uploaded files parsed as data only; formulas are not executed.
- Exported spreadsheet cells beginning with formula characters are escaped to reduce formula-injection risk.
- Google key restriction guidance documented in the README.

## 15. Observability and failure behavior

Structured logs include:

- Request ID.
- Operation and elapsed time.
- Task/location counts.
- Matrix cache hit/miss counts.

Expected failures have actionable messages:

- Backend unavailable.
- Google credentials missing or rejected.
- Geocoding ambiguity or failure.
- Google quota/rate limit.
- Partial/unreachable matrix.
- Invalid import columns or values.
- Solver timeout.
- Strict-plan infeasibility.

## 17. Canonical test scenarios

These fixtures will be committed as non-sensitive sample data and reused at domain, solver, API, and UI levels.

### Scenario A — Three-truck feasible mixed plan

- Three trucks with differing capacities.
- At least two pickup tasks, two drop tasks, and two pickup–drop pairs.
- Multiple readiness times and deadlines.
- All tasks feasible within one or two days.
- Expected: `FEASIBLE`, no late/unassigned task, validated routes.

### Scenario B — Capacity impossible

- One task exceeds every truck capacity.
- Expected: precheck failure with `CAPACITY_EXCEEDED` and no solver call required for that task.

### Scenario C — Deadline individually impossible

- Due time earlier than the lower-bound travel plus service completion.
- Expected: `DEADLINE_IMPOSSIBLE_INDIVIDUALLY` with earliest estimated completion.

### Scenario D — Collective fleet shortage

- Every task is feasible alone, but three trucks cannot complete all work before deadlines.
- Expected: `PARTIALLY_FEASIBLE`, partial route plan, affected POs, and `INSUFFICIENT_COMBINED_FLEET_TIME`.

### Scenario E — Pair precedence

- Pickup–drop tasks where a distance-only route would prefer the wrong order.
- Expected: pickup always precedes delivery on the same vehicle.

### Scenario F — Multi-day shifts

- Tasks across at least two days with one physical truck represented by separate shifts.
- Expected: no overlapping use and no cross-shift continuous route.

### Scenario G — Routing failure

- Mocked unreachable element, partial response, throttling, and invalid credentials.
- Expected: controlled provider error and no invalid matrix/plan.

### Scenario H — Timezone boundary

- Date-only deadlines and daylight-saving edge cases.
- Expected: explicit normalization or row-level rejection; no silent one-hour shift.
