# Reference Application Behavior Notes

**Reviewed source:** `../../CVRP_PDP_Streamlit-master/app2.py`  
**Reviewed documentation:** `../../CVRP_PDP_Streamlit-master/README.md`  
**Review date:** 2026-06-21  
**Purpose:** Preserve useful behavior while preventing reference limitations from becoming new requirements.

## 1. Reference application summary

The reference is a single-file Streamlit application that accepts locations, signed demands, vehicle capacities, and pickup–delivery index pairs. It geocodes addresses with Nominatim, calculates a straight-line geodesic distance matrix, solves a capacitated pickup-and-delivery routing problem with OR-Tools, and displays route tables, a Folium map, and a CSV export.

All UI, application state, geocoding, matrix generation, optimization, mapping, and export logic are contained in `app2.py`.

## 2. Observed workflow

1. User selects the number of locations and vehicles in the sidebar.
2. User enters one depot address and the remaining addresses.
3. The app inserts a hidden duplicate of the depot into its address/node arrays.
4. User explicitly requests geocoding and distance-matrix calculation.
5. User enters signed demand values:
   - Positive means pickup.
   - Negative means delivery.
6. User enters each vehicle capacity.
7. User defines pickup–delivery pairs by node index.
8. User reviews an internal data dictionary and starts the solver.
9. The app shows routes, total distance, load, a map, and a CSV download.

## 3. Behavior retained conceptually

| Reference behavior | New-project treatment |
|---|---|
| Explicit plant/depot input | Retain with a first-class plant model. |
| Configurable fleet size and capacities | Retain with named vehicles and dated shifts. |
| Pickup and delivery precedence | Retain and extend to all task types through internal task expansion. |
| Same vehicle for a pickup–delivery pair | Retain as a hard constraint. |
| OR-Tools routing foundation | Retain behind a backend solver interface. |
| Explicit calculate/solve buttons | Retain to control cost and avoid Streamlit-rerun side effects. |
| Route table and map | Retain with ETA, service, deadline, slack, and stable colors. |
| CSV export | Retain and add XLSX plus infeasibility data. |

## 4. Behavior intentionally replaced

### 4.1 Application structure

**Observed:** Streamlit imports and calls geocoding, OR-Tools, map, and export logic directly. State is stored in `st.session_state`.

**Replacement:** A standalone FastAPI backend owns validation, Google integration, optimization, diagnostics, and persistence. Streamlit is an HTTP client and holds draft UI state only.

### 4.2 Address and distance calculation

**Observed:** `geocode_address` uses Nominatim and waits one second. `calculate_distance_matrix` computes symmetric geodesic distances between coordinates.

**Replacement:** Google Geocoding resolves addresses and Google Routes `Compute Route Matrix` supplies asymmetric road distance and duration. The backend caches and validates results. Production planning never silently falls back to straight-line distance.

### 4.3 Depot duplication

**Observed:** The app duplicates the depot at indices 0 and 1 and adds special zero-distance handling between those indices. The duplicate is partially exposed as a selectable location.

**Replacement:** The public model has one plant location. Internal virtual plant nodes may be generated by task expansion but never leak into user data or API contracts.

### 4.4 Demand entry

**Observed:** Users enter signed demands. The capacity dimension starts at zero and assumes load changes are directly valid along the route.

**Risk:** A standalone negative delivery can be infeasible from zero starting load unless a corresponding pickup occurs first. Signed input is also error-prone for planners.

**Replacement:** Users always enter a positive quantity. Every movement expands to a pickup and delivery pair, including plant-origin drops and plant-destination pickups. The backend produces internal load deltas.

### 4.5 Scheduling

**Observed:** The solver contains a distance dimension and capacity dimension only. There are no readiness times, service times, due dates, truck shifts, or ETAs.

**Replacement:** A time dimension enforces readiness, service completion deadlines, waiting, shift windows, and route-duration limits. Multi-day planning uses separate dated shifts for each physical truck.

### 4.6 Solver configuration and status

**Observed:** The solver uses parallel cheapest insertion and has no explicit time limit or local-search configuration. A null solution becomes the generic message “No solution found.”

**Replacement:** Solver limits and strategies are explicit and recorded. Timeout, invalid input, strict infeasibility, partial diagnostic feasibility, and success are distinct statuses.

### 4.7 Feasibility explanation

**Observed:** No task-level diagnostics are returned.

**Replacement:** Static prechecks, earliest-completion checks, a strict solve, and a relaxed diagnostic solve identify capacity, address, compatibility, horizon, deadline, collective-fleet, timeout, and unknown causes.

### 4.8 Route metrics

**Observed:** Optimization distance is calculated from one matrix, while displayed leg distance is recalculated geodesically. `total_load` sums final route loads rather than reporting transported quantity or maximum route load.

**Replacement:** All displayed route metrics are derived from the exact matrix/result used by the solver. The result reports transported quantity, load after each stop, and route peak load separately.

### 4.9 Map behavior

**Observed:** Routes are straight Folium polylines between coordinates, and colors are randomly regenerated.

**Replacement:** Vehicle colors are deterministic. Route order always comes from the validated backend plan. Road polylines may be requested explicitly when enabled, while the table remains the source of operational truth.

### 4.10 Validation and persistence

**Observed:** Validation checks mostly compare list lengths. Address, pair, quantity, and schedule semantics are not modeled. Data disappears with session reset.

**Replacement:** Typed contracts provide row/field errors. SQLite stores scenarios, plans, and cached matrices behind repository interfaces.

## 5. Reference implementation risks not to reproduce

- Streamlit-specific calls inside geocoding and map helpers.
- Broad exception handling that converts distinct provider failures into `None`.
- Hidden node-index conventions in user-facing data.
- Direct mutation of business data during widget reruns.
- No invalidation of a previous solution after all input changes.
- No independent validation of extracted solver routes.
- No explicit Google/API cost controls.
- No distinction between solver timeout and infeasibility.
- Random map styling that changes between renders.
- Encoding artifacts in displayed symbols.

## 6. M0 conclusion

The reference is suitable as a conceptual demonstration of capacity and paired routing. It is not suitable as an architectural base. New implementation will preserve the recognizable planner workflow and OR-Tools concepts while rebuilding domain, routing, solver, API, and UI boundaries under the approved project plan.
